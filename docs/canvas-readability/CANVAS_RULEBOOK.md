# ArchBro 架構圖閱讀規則草案

日期：2026-09-06。草案修訂：0.2（納入補充工具研究）。狀態：使用者已授權在 feat/canvas-readability-20260906 實作。這是設計契約；實際證據與限制另見 README.md。

使用者已定案：首次全圖入鏡、完整展開所有架構層級、隱藏不必要的詳細文字、總覽只顯示主流程、選取元件後揭露其他相關連線。主流程預設代表專案的跨系統主幹，另可切換具名業務流程。參考 Archify 的閱讀方式，保留 ArchBro 自己的視覺與治理機制。

以下具體布局與顯示細則是依上述決策整理的建議預設；實作依此進行；每一項仍須對照測試證據，不能直接當成驗收成績。

本次新增參考的採用理由與不採用項目，見 [REFERENCE_SYNTHESIS.md](REFERENCE_SYNTHESIS.md)。其中區分官方文件可確認的概念與 ArchBro 自己的設計判斷。

1. **先看懂全貌，再讀細節**

   - 首次開啟普通 Canvas，將完整架構邊界放入可用畫布。工具列、頁尾與側欄不得遮住已宣稱入鏡的內容。
   - Project 是圖的範圍，不新增一個 Project 節點，也不畫 Project 到每個 Root 的假依賴。
   - 所有架構層級預設展開。遠景仍看得到子系統與元件的存在、歸屬及主要路徑。
   - 「完整展開」只描述階層；文字揭露與連線顯示各有獨立規則。
   - 沒有選取時，側欄保持精簡，解釋如何閱讀當前主幹，不堆滿狀態、任務及技術欄位。

   | 閱讀狀態 | 圖上顯示 | 按需查看 |
   | --- | --- | --- |
   | 全圖總覽 | 邊界名稱、可辨識的元件短名、主幹箭頭、少量必要提示 | 責任描述、完整關係文字、任務、證據、ID、版本明細 |
   | 放大閱讀 | 更多元件名稱與必要的類型識別 | 長段落仍由 Inspector 承接 |
   | 選取元件 | 元件及相關方向清楚突出，其他架構留作上下文 | 完整名稱、責任、所有直接輸入／輸出關係 |
   | 選取關係 | 清楚標示起點、終點及該條路徑 | 關係語意、描述、來源、證據、Canonical ID |

   - 字級小到無法辨識時，次要文字可以隱藏；元件本身與歸屬框仍保留。不得用一片細小文字冒充可讀的全貌。
   - 中文、英文、長識別字及混合文字都按實際字寬排版，不以空格或字數估算代替邊界檢查。
   - 建議元件名稱最多兩行，邊界名稱一行；溢出時安全省略，完整名稱可在選取或提示中讀取。
   - 不重複顯示 SERVICE · SERVICE 等資訊。普通卡片不常駐責任段落、任務清單、depth、技術 ID。
   - Zoom 只改顯示密度與鏡頭。放大不重新排圖、不改元件大小的 canonical 值、不換一套關係資料。
   - 有效的元件 deep link 是明確例外：可以直接選取並帶入視野；Fit 隨時回完整全貌。

2. **布局先有結構，再處理密度**

   - Backend 擁有節點座標、容器範圍、連線端口與路徑。Frontend 不猜 layer、不重新跑 layout、不靠拖曳改 accepted Architecture。
   - 同一份架構資料、Architecture version 與 Layout algorithm version，必須得到相同幾何。更換視窗、重新載入、選取、Zoom 不得改變它。
   - 改變布局演算法必須能識別新 layout version；不得讓同一套布局識別在不同 runtime 指向不同幾何。
   - 排版可評估現有引擎。使用 ELK、React Flow 等工具本身不代表產生第二套真相；真正的邊界是 Backend 發布幾何，Frontend 不自行改 canonical 模型或重排。本草案尚未決定換引擎或 renderer。
   - 比較布局前固定輸入正規化、引擎版本／選項、節點尺寸與字體度量政策。先滿足語意、包含、文字與避障等硬條件，再比較交叉、彎折、線長與緊湊度。
   - 最上層先依 canonical hierarchy 劃分責任域，再容納各自子系統及元件。父框必須包住所有子項與必要留白。
   - 同層容器／節點不可重疊；父子容器合法巢狀不算碰撞。容器標題有自己的空間，子卡片不能頂到標題。
   - 建議主幹以左至右為優先閱讀方向，分支與共享能力向下安排；外部系統安排在外部區。分類來自 canonical semantic kind／role，不能靠名字猜。
   - 多個責任域按實際關係的穩定順序排列；需要換行時用清楚的排列與跨區通道，不為了硬擠一排拉出過寬畫布。
   - 小子集合採簡單單列／單欄；大集合用可重現的整齊網格。嵌套子系統要避免堆成狹長高塔。
   - 布局先滿足包含、留白及路由通道，再改善跨區線長與交叉；最後才壓縮多餘空白。不能為了緊湊犧牲可讀性。
   - 資料儲存／共用設施／外部依賴可以有穩定的語意區，但不能把真正屬於某個父系統的元件移出 canonical containment。
   - 不能為了「每個地方都有連接」補造關係。真正孤立的元件要指出尚無已接受關係，交由架構內容檢查處理。

3. **線必須說清楚：誰對誰做了什麼**

   - Canonical relationship 的 ID、source、target、方向、type、描述及 provenance 不因畫面簡化而消失。
   - 整份關係資料與對應路徑可供閱讀互動使用；總覽只畫 Backend 指定的主幹集合。
   - 主幹是結構摘要：只選用已存在的 canonical edges，保留實際跨系統聯繫，不能宣稱它就是唯一的業務執行順序。
   - 主幹顯示規則需由 Backend 明確定義、可重現、有版本；不能交由 browser 依名字、座標或任意排序猜出。
   - 具名業務流程需有明確來源、名稱、節點順序及對應的已存在關係。三個樣本先用各自既有的三條固定流程；不得臨時生成漂亮但無來源的流程。
   - 持久化閱讀視圖具有穩定 view ID、project／Architecture version、所引用 node／edge IDs、用途與來源。鏡頭、當下選取及 hover 是另一層暫時狀態，不存成 accepted Architecture。
   - 具名流程是架構的閱讀／解說，並非觀測到的 production 執行紀錄。邊的依賴方向不能自行推成事件先後、因果或 runtime impact。
   - 流程必須綁定可驗證的架構資料／版本。資料改變後，失效路徑不得偷偷改接其他節點而保留舊流程名稱。
   - 切換具名流程只切換顯示／突出哪些關係。所有元件及容器留在原位，不重建另一張架構。
   - 選取元件，補出其所有直接 canonical 輸入／輸出關係；上下游多跳另用明確的 Upstream／Downstream 功能。
   - 提供「全部關係」讀取模式，供核對完整關係。這是顯示選項，不修改 accepted Architecture。
   - 計數必須分開：目前顯示 X 條／全部 Y 條。Collapse、Isolate 與流程過濾後也須反映實際顯示集合。
   - 一條線有明確出入口與指向 target 的箭頭。A → B 與 B → A 分開呈現，不合併成一條意義不清的雙箭頭。
   - 同方向的多條不同語意關係，也各自可識別、可選取；不可只剩「N relationships」而無從辨識每條方向與行為。
   - 建議採用正交主路由及穩定端口，預留不同關係的進出間距。線不得穿過元件卡片、邊界標題或遮住文字。
   - 回呼、回流、循環遵守真實方向；利用獨立回流通道表達，不為了全圖看起來單向而反轉箭頭。
   - 跨越容器的路徑要清楚連回其內部真正端點，不能讓容器邊框看起來像新的 service 或 routing hop。
   - 線的交叉不等於連接。沒有 canonical junction 的地方不得畫出表示匯流的實心接點。
   - 預設隱藏大部分長連線文字。必要短標籤緊鄰所屬路徑；擠不下就移到 Inspector，不能拋到遠處而無法對線。
   - 若採編號，編號必須對應同一條 edge 的 Inspector 項目，選取後才出現；不能把全圖又塞滿數字。
   - 色彩與線型有固定語意且使用少量種類。架構類型與健康狀態要能區分，不讓同一顏色同時代表兩種互相衝突的意思。
   - 若來源已有資料，關係可連到 API／message／schema／契約版本與文件，細節由 Inspector 及 Agent 按需讀取。未知協定、endpoint、schema 維持未知，不為補完整畫面而猜測。
   - 分開 containment、dependency、call、message、ownership 等不同意思。讀取同一關係的 inverse 不能算成另一條業務回呼；owner metadata 不能拿來授予執行權限。

4. **閱讀互動各司其職，而且可回復**

   | 操作 | 應有行為 | 不可產生的副作用 |
   | --- | --- | --- |
   | 選取 | 突出元件、直接關係及方向，開啟既有 Inspector | 重排、突然跳到另一張圖、改 accepted Architecture |
   | Focus | 原圖仍在，與目前查詢無關部分淡化 | 把淡化誤作刪除、隱藏必要祖先邊界 |
   | Isolate | 顯示原子樹、祖先／邊界及必要外部端點與跨界關係 | 建造替代拓撲、擴張到無關的外部鄰居 |
   | Collapse | 本地隱藏子項與內部線，保留容器及可理解的跨界聯繫 | 寫回架構、拉直成穿過卡片的假路線 |
   | Expand | 恢復原座標、子項與 canonical 路由 | 新的排列、重建 ID |
   | Clear | 清除選取／Focus 等暫時狀態，回到目前選定的閱讀流程 | 刪除內容或無提示地改成別的流程 |
   | Fit | 當前閱讀範圍完整入鏡；完整視圖下就是整個專案 | 自動折疊層級以塞入畫面 |
   | Trace Path | Backend 查詢 canonical directed relationships，再突出結果 | 由 SVG 自行推斷路徑或宣稱 runtime impact |

   - 重新載入普通 Canvas 回到完整展開與專案主幹；Deep link 的明確選取例外照實套用。
   - Inspector 保留 Overview、Dependencies、Tasks、Evidence、Code、Decisions 六個入口。名稱／責任／相關方向優先，技術明細依頁籤揭露。
   - 點線後可直接辨識 From、To、方向與行為；詳細描述、ID、provenance 仍完整保留，不以省略圖中文字為由刪掉資料。
   - 無 Code Truth snapshot 時明說沒有；Observation、Code 與 Agent 發現只能成為證據／建議。
   - 普通 read、focus、isolate、collapse、context、observation、task interaction 不改 accepted Architecture。
   - Structural recommendation 維持 PENDING。只有明確 Human Review Accept 才能令 accepted Architecture version 增加。
   - 畫面過濾不能暗中改 Agent 的 context 邊界。Context Tray 顯示與送出的 server manifest 仍需一致；原本的 auth/provider/治理契約繼續生效。
   - Agent 按問題取有界的 canonical 資料，不以 DOM／SVG 當作工程事實，也不必每次送全量。回應交代版本、scope、IDs、限制與是否截斷；未顯示、查詢不完整與確定不存在必須區分。
   - 證據來源方法、架構接受狀態、來源有效性分開記錄。直接擷取不等於 runtime observed／accepted；人審接受推論不會把其來源改成直接觀測。過期與未知不能用信心分數掩蓋。
   - Invalid deep link fail soft；畫布仍可讀，架構不變。

5. **用同樣本、同流程、同畫面判定是否改善**

   固定輸入保持不變：

   | 參考樣本 | 元件／邊界節點總數 | Canonical relationships | 固定業務流程 |
   | --- | --- | --- | --- |
   | 01 電商訂單到交付 | 36 | 42 | 既有 3 條 |
   | 02 協作與 AI 工作平台 | 40 | 63 | 既有 3 條 |
   | 03 智慧製造與供應鏈 | 40 | 76 | 既有 3 條 |

   - 保留既有 project、stable IDs、Architecture version、資料 hash。不得縮減元件／關係，或重生較容易畫的樣本來製造改善。
   - 固定每次輸入與產生步驟；記錄 source、layout version、viewport、縮放、reading view 與選取狀態，才能比較。
   - 每個樣本比較：首次 Fit 總覽、既有三條具名流程、固定元件的直接關係、100% 文字閱讀、Collapse → Expand、Clear → Fit。
   - 最基本的資料驗收：所有 canonical IDs／方向一致；主幹與流程只引用現有 edges；選取可取回被總覽隱藏的關係；顯示數與總數正確。
   - 最基本的幾何驗收：同層無重疊、子項在父框內、線不穿卡片／標題、箭頭落在正確 target、可見文字無溢出、標籤可對回路徑。
   - 可重現驗收：打亂輸入順序仍得到相同幾何；Zoom／選取／流程切換不改 canonical geometry；Collapse → Expand 可還原。
   - 無法保證任何大型圖都零交叉。必須量測交叉、共線、路線長度與遮擋，並檢視實際圖；不可只靠 API PASS 宣稱清楚。
   - 比較交叉數時，必須註明顯示的是哪些 edges；不能拿新主幹子集和舊全關係畫面直接比數字。
   - 人眼驗收至少能回答：這個專案有哪些責任域？某個元件屬於哪裡？主幹怎麼串？誰呼叫誰？怎麼查看被隱藏的關係？
   - 三個樣本都需保存相同條件的實際畫面與發現；不能只挑最好看的一張。
   - 人類與 Agent 對照回答同一組閱讀問題。人類能辨認關係與找回細節；Agent 引用正確 IDs／版本，標示推論與查詢限制。這些結果需日後實測，不能預先宣稱最佳。
   - 真正渲染的文字、箭頭、遮擋與裁切必須檢視；DOM 邊界檢查只是一部分。加入中文／長識別字、鍵盤操作及字體替代的閱讀檢查。
   - 目前固定樣本為 36–40 個架構節點；通過它們不等於已證明數百／數千節點的全展開可讀性。
   - 本次僅實作與執行受影響的 focused checks。14V／15D 與正式部署不包含在本次離線驗證中，不盲跑既有長套件。
